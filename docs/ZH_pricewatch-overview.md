# 概览

这是一个个人产品价格跟踪与订阅支出管理系统，由云端 Web 应用、本地私有管理界面和本地抓取流程组成。

## 问题

系统将两个领域分开处理：

- **Product**：跟踪产品价格、来源、目标价格、价格历史和抓取结果。
- **Subscription**：记录周期性订阅支出，主要包括订阅名称、月费、货币和归档状态。

云端应用负责管理产品、订阅、审核流程和价格历史。本地管理界面负责抓取操作和调度。数据库中的数据作为单一事实来源。

本项目的目标是跟踪产品价格和每月订阅费用，以找到更便宜的产品、将订阅支出控制在预算内并节省开支。系统还应具备清晰的职责划分、一致的约定、稳定的运行以及长期可维护性。

## 权衡

### 多来源产品价格比较

每个 Product 可以包含多个商店来源。系统会同时存储来源价格和数量信息，然后计算标准化单价，以便公平比较不同包装规格。

例如：

```text
100 SEK / 2 kg => 50 SEK / kg
```

### 分离 Product 与 Subscription

早期版本的 Subscription 复用了过多 Product 概念。随着项目演进，这两个领域被明确分离：

- **Product** => 价格跟踪
- **Subscription** => 周期性支出跟踪

这样可以保持 Subscription UI 简洁，并防止 Product 特有的跟踪逻辑渗透到 Subscription 领域。

### 共享前端基础

Cloud Web 和 Private Web 是两个相互独立的 Next.js 应用。它们不共享页面级业务逻辑，但会通过 npm workspaces 共享以下基础能力：

- 设计系统
- UI 组件
- 共享类型 / 工具函数
- HTTP 基础设施

这样既能保持应用职责分离，又能避免重复建设基础代码。

### 单一生产数据库

云端服务和本地生产组件使用同一个 Neon PostgreSQL 生产数据库。因此，本地抓取结果、Cloud Web 操作和 Web API 数据都基于同一个事实来源，从而降低维护和同步多个数据库的复杂度。

### 分离云端与私有组件

Cloud Web 和 Web API 可以独立部署，而抓取编排和浏览器自动化则保留在受信任的本地设备上。这样设计的主要原因是，一些云服务提供商不支持基于浏览器的抓取工作负载，同时一些目标网站也会阻止来自云环境的抓取流量。
